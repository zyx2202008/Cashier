# 客户与供应商编码更新说明

本更新基于原 1.0.6 项目。Windows 发布文件位于交付包的 `Cashier` 目录，完整源码和测试位于 `源码` 目录。此包不包含实际账套或测试账套。

## 使用与升级

1. 关闭所有正在使用该账套的旧版或新版程序，先另行备份真实账套，再完整解压此包。
2. 在 Windows 上打开 `Cashier/Cashier.exe`。首次打开旧账套时，程序会在该账套的 `backups` 文件夹生成一份升级前备份，然后自动升级数据库。默认账套位于 `%APPDATA%\Cashier`；自定义账套使用其自身目录。
3. 列表和编辑窗口继续使用同一编码字段；新增和编辑时不可手工输入编码。新编码在保存成功时确定，窗口中的提示不代表已预留号码。
4. Excel 等软件外部已保存的旧供应商编码不会自动改写；导入前请重新下载模板，按软件中的当前编码更新这些文件。历史审计和导入结果保留当时的记录。

仅在隔离测试账套上测试了升级，没有改动用户实际账套。交付的独立 `Cashier.exe` 已在隔离账套完成首次启动、界面和重启测试。实际账套升级前仍请先备份并核对升级结果。

## 规则与兼容性

- 新客户使用 `KH-0001` 起的序列，纯供应商使用 `GYS-0001` 起的独立序列，至少四位数字，超过 9999 后自动扩展。普通新增和发票快捷新增共用同一套服务。
- 原有“客户与供应商”兼有类型保留，新增时使用客户 `KH` 序列。升级时，现有客户和兼有类型的记录及其编码均保留；现有纯供应商的合规 `GYS` 编码在无冲突时保留，其他纯供应商分配新的 `GYS` 编码。升级后实际起始号码取决于历史编码和审计记录，未必从 0001 开始。
- 修改单位类型时，跨客户/供应商编码类别会分配新编码；历史兼有类型改为纯客户时，如原编码不符合客户格式，也会分配新编码。内部 ID 保持不变，原有业务身份校验仍然生效。
- 分配、资料保存和审计日志使用同一个数据库写事务。失败回滚编号，不复用成功分配后删除的编号；数据库原有的编码唯一约束继续生效。
- 升级前从现存资料和往来单位审计记录中恢复历史流水上限，避免重新分配可查到的旧号码。旧版已删除且没有留下审计记录的号码无法从现有数据库推知。恢复更早的账套备份也会使流水回到备份时点，恢复后需核对备份之后曾使用的编码。
- 升级检测保留记录的大小写编码冲突及超出支持范围的历史序号。如无法安全升级，会整体回滚并提示检查；请保留原账套和自动备份，不要手工删除记录。

## 数据库与业务关联

数据库从版本 2 升至版本 3；版本 1 也会顺序升级。沿用 `partners.code`，不增加往来单位编码字段，也不新增业务表；在原 `meta` 表中保存两类序列上限。升级在事务中执行，失败时不会留下部分供应商改码。每次迁移改码保留一条含原、新编码的审计记录。

已检查本项目的凭证、发票及报表关联：数据库通过 `partner_id` 关联，迁移只更新编码，不修改 ID。旧审计内容不覆盖，便于追溯。

## 测试结果

- 编码及升级专项：36 项通过，包括两类独立编号、删除不复用、混合新增、重新打开、手动编码无效、类型转换、插入/审计失败回滚、48 次并发写入、4 个独立进程并发写入、四位数扩展、v1/v2 迁移、冲突和失败回滚、旧备份恢复、ID/外键和升级前备份。
- 窗口专项：5 项通过，验证编码只读、类型切换提示以及失败后的显示。发布版 EXE 在隔离账套运行发票快捷新增界面验收，首次 30 项及重启后 6 项通过，重启后分别验证了两类编码继续递增。
- 原有 12 组业务回归通过，包括 15,284 项压力计算、725 项状态计算、368 项期间报表、发票批量导入和客户身份校验。为适应自动编码，少量旧测试改为读取实际分配的编码；报表历史编码用例保留专用旧数据夹具。
- Release 构建和 win-x64 自包含发布成功。构建中保留项目原有的空值和未使用字段警告。
